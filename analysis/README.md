# Newton 3 — Analysis

Audits and benchmarks over the prototype in [`src/newton`](../src/newton). These run like
the tests do — against the synthetic example dataset or synthetic baselines — and exist to
answer one question with evidence: **does the behaviour layer actually do what the design
claims?** Importing the package puts `src/` on the path, so every module `import newton`
whether run via `python -m analysis.<module>` or under pytest.

The dataset under [`docs/artifacts`](../docs/artifacts) is fully synthetic, generated by
[`generate_synthetic_data.py`](../docs/artifacts/generate_synthetic_data.py).

Each module reads, none writes back to the score: the behaviour score stays a pure,
explainable fold (see [`src/newton/README.md`](../src/newton/README.md)). Analysis observes
the engine; it never couples to it.

## Modules

| File | Role |
|---|---|
| `impact.py` | Data audit: scores the ~1200 underserved users in the Metabase dataset and shows the behaviour layer separates abuse (tiers M, X) from the high-demand underserved (A, B, C). Writes `REPORT.md`. |
| `predict.py` | The ML stretch: a dependency-free logistic-regression no-show predictor that feeds **capacity** (overbooking factor), never **ranking** — so a learned model can never make an allocation unexplainable. |
| `shadow.py` | Shadow-mode evaluation: rank the new behaviour ordering against a mock legacy (priority-only) ranking, **within each admin-priority bracket** — where behaviour is the sole differentiator. |
| `scenarios.py` | Deterministic edge-case studies — decay, per-event timers, escalation, reward cap, floor, explainability, tiers — a readable walkthrough for the demo. |
| `REPORT.md` | Generated output of `python -m analysis.impact`. Regenerate; do not edit by hand. |

## What the audit finds

- **Defaults barely move the score** — the short no-show window hides a 3-month history.
  A real finding, and the argument for tenant-configurable windows.
- **Long memory separates cleanly** — tiers M (multi-misser) and X (excess nudges) sink;
  the high-demand underserved A, B, C keep near-base scores.
- **The behaviour layer acts where the legacy system used a coin-flip** — nearly every user
  shares an admin-priority bracket with someone else, replacing a random tie-break with a
  deterministic, explainable order.

The full numbers, with method and honesty caveats, are in [`REPORT.md`](REPORT.md).

## Run

From the repository root:

```bash
python -m analysis.impact      # data audit → prints summary, writes analysis/REPORT.md
python -m analysis.predict     # train the no-show model → fit + overbooking factor
python -m analysis.scenarios   # deterministic edge-case walkthrough
pytest tests/test_shadow.py tests/test_predict.py   # the analysis tests
```

## Honesty notes

The Metabase dataset gives 3-month *aggregates*, not an event log. `impact.py` reconstructs
events by spreading each user's counts evenly across a 90-day window and scoring at a fixed
reference date (`2026-06-01`) — so it models *recent standing*, not lifetime totals, and is
fully reproducible. `predict.py` trains on the empirical no-show rate and excludes the
features that encode it, to avoid label leakage. Both are baselines that prove the shape;
production retrains on the real event log that `newton.store` now captures.
