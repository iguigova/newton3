# Newton 3

> A behaviour-driven allocation engine for shared workplace resources — transparent, fair,
> and AWS-native.

**Newton** decides who gets a shared space (parking, a desk, an EV charger) when demand
exceeds supply. **Newton 3** keeps the conventional admin-controlled priority layers but
adds a per-user **behaviour score** as a third signal, so that *how you've used the system*
— showing up, releasing spaces you won't use, carpooling, avoiding offences — influences
how you rank in the next allocation.

This repository holds the design, a runnable Python prototype, a synthetic example dataset,
and an analysis that audits the behaviour layer against that data.

---

## What problem it solves

A legacy, rule-based allocator ranks users with opaque logic. The recurring complaints are:
*"allocation feels random"*, *"I never get Tuesdays and nobody tells me why"*, and *"I was
penalised for a no-show I didn't commit."* Newton 3 targets three things those complaints
demand:

- **Transparent** — every allocation decision should be explainable to the user.
- **Fair** — behaviour-driven incentives, not invisible rules.
- **Scalable** — a serverless, event-driven AWS architecture, AI-ready.

## How it works

Allocation priority is applied in layers; the behaviour score is the new third layer:

```python
def allocation_sort(user):
    return (
        user.group_priority,    # Layer 1 — admin-controlled group (existing)
        user.user_priority,     # Layer 2 — admin override (existing)
        -user.behavior_score,   # Layer 3 — system-controlled behaviour (NEW)
        random(),               # Layer 4 — tie-breaker
    )
```

Each user starts at `base_score = 100`. Events nudge the score up or down, and it
recovers over time:

| Event | Points | Window |
|---|---|---|
| Unused booking (no-show) | **-3** | Allocation cycle |
| Free / non-paid space usage | **-1** | 2 weeks |
| Offence (rule violation) | **-5** | 4 weeks |
| Carpool participation | **+5** | — |
| Decay (recovery) | **+2 / week** since last penalty | up to base 100 |
| Reward cap | **+20 max** | rolling 4 weeks (anti-gaming) |
| Floor | `max(score, 0)` | hard minimum |

Scores map to user-facing tiers (Platinum 150+ / Gold 120–149 / Silver 80–119 /
Bronze 50–79 / Restricted <50).

> ⚠️ Several of these mechanics have open design questions and known tensions (e.g. the
> +20 cap makes Platinum unreachable from base 100; the free-space penalty is contested;
> decay is modelled globally rather than per-event). See the
> [design decisions & critique](docs/README.md#design-decisions--critique) in the docs.

## Target architecture

Serverless, event-driven, multi-region — a legacy service remains source-of-truth only
during a shadow-mode migration:

```
Legacy service (source-only) ─► Migration Script ─► AWS Isolated Stack (Newton vNext)

  EventBridge Bus ─┬─► Scoring Lambda      (read/write score, append event)
                   ├─► Decay Lambda         (weekly, EventBridge schedule)
  Newton run      ─┼─► Allocation Lambda    (fetch score + tenant config, sort, emit)
  Identity API    ─┴─► API Lambda           (GET /users/{id}/behavior-score)

  DynamoDB: behavior-score · behavior-events · tenant-config
  Global Tables → EU eu-west-1 + US us-west-1
                   │
                   ▼  Shadow-mode Comparator (parity vs legacy output)
```

## Status

Working Python prototype in [`src/newton/`](src/newton): scoring engine, allocation
ranking, event store, read API, a runnable HTTP server, and a CLI simulator, with tests.
The core insight —
behaviour score as a pure fold over an event log — is documented in
[`src/newton/README.md`](src/newton/README.md).

```bash
pytest                       # run the tests
python -m newton.cli demo    # event stream → ranking + a behaviour-score response
python -m newton.app         # serve the read API on :8000, then:
curl -s localhost:8000/users/bob/behavior-score
```
