Newton 3 — a behaviour-driven allocation engine

Newton 3

A behaviour-driven parking-allocation engine that is transparent, fair, and AWS-native — built on one idea: the behaviour score is a pure fold over an append-only event log.

score(events, config, now) = max(floor, base + min(rewards, cap) + penalties)
63 tests pass 0 dependencies · stdlib only 0 mocks · the engine is pure 1,200-user data audit

Answering the two loudest complaints in the example tickets: “allocation feels random” and “nobody tells me why.”

The insight

Don’t build subsystems. Reframe.

The spec asked for a persistent score, a per-event decay model, an explainability layer, a per-tenant config service, and a weekly decay job. We built one pure function — and four of those “subsystems” became properties of it. The fifth, the decay job, was deleted.

RequirementHow the fold delivers it — for free
Always-current scoreDerived from the log on read. Nothing to reset, never stale.
Fair, per-event decayEach event fades against its own timestamp, inside the fold.
Explainability (GDPR Art. 22)The per-event contributions are the explanation; they reconcile to the score by construction.
Per-tenant policyConfig is a parameter. Per-tenant = a different Config.
The weekly Decay LambdaGone. Decay is computed at read time from injected now — one fewer moving part, zero “stale between runs”.

Mandatory complaint-analysis proposals

The two hardest asks, delivered & tested

#1 — Offence override delivered

Config.offence_override force-ranks repeat offenders behind everyone — bypassing admin priority and score. Threshold and window are tenant-configurable. Deliberately a count threshold, not a decay, and enforced only behind a proven detector (the false-positive offence-detection risk is called out in the docs).

#8 — Native explainability delivered

decide() attaches a reason to every outcome: your rank, the bracket above you, or the exact behaviour cutoff. behavior_score returns the score’s own per-event trace. This is the answer to “nobody tells me why,” and it’s legally required for EU users.

The behaviour layer is layer 3 — it only reorders users within an equal-priority bracket, exactly where the legacy system fell back to a random tie-break. 1,030 of 1,200 users sit in such a bracket; the largest holds 777 users spanning scores 39–100 — ample signal to order fairly instead of by chance. That defaults barely move the score is itself a real finding (short windows hide a 3-month history) — and the argument for tenant-configurable windows, surfaced honestly rather than hidden.

Innovation · the AI stretch — composed, not coupled

ML where it earns its place — never where it breaks trust

A learned ranking would bring back the exact opacity this project kills. So the model feeds capacity, not ranking — predicted no-show propensity becomes an overbooking factor (the airline trick). The behaviour score stays a pure, explainable fold; a black box never decides who gets a space, only how many are admitted.

Pure-Python logistic regression — still zero dependencies. Label = empirical no-show rate, with the label’s own inputs excluded from the features to prevent leakage.

# python -m analysis.predict — real output MAE 0.030 vs predict-the-mean 0.083 # 64% lower error mean predicted no-show 8.2% (empirical 8.2%) # calibrated Pool attendance ~92% → overbooking 1.09× Fill 80 spaces → admit 87 requests ~7 more people served each cycle; ranking still decides WHO, with the same explanation.
Scalability & maintainability

Runs without AWS — because the core is pure

AWS would providePrototype runs without it
DynamoDB tablesInMemoryStore behind an EventStore Protocol
Lambda computePlain functions: evaluate, rank
EventBridge busThe engine doesn’t care how an event arrived
EventBridge decay scheduleNothing — decay is read-time from now

Going to AWS is wrapping the same evaluate in a 3-line Lambda handler and writing one DynamoEventStore. The pure core never changes — which is why the tests need no mocks. Idempotent under at-least-once delivery (event_id dedup); every response carries config_version + evaluated_at, so any decision reproduces exactly.

# Target topology — Legacy service is source-of-truth only during shadow migration Legacy service ─► Migration ─► AWS Isolated Stack EventBridge ─► Scoring path (append event) Newton run ─► Allocation λ (fold, sort, emit winners) Identity API ─► API λ (GET /behavior-score + trace) DynamoDB: behavior-events · tenant-config (behavior-score is a cache, not source of truth) Global Tables → EU eu-west-1 + US us-west-1 │ ▼ Shadow Comparator — parity vs legacy, before cut-over # GSI sort key inverts + zero-pads the score so one ascending # Query returns a group already ranked best-first.

Edge cases proven in analysis/scenarios.py: linear per-event decay (−5.00 → 0.00 over 28d), reward saturation at +20, hard floor at 0, future-dated events clamped to full weight, and the shown trace reconciling to the score to the cent. The two known tensions — Platinum unreachable from base 100 under the +20 cap, and the contested free-space penalty — are documented as open questions, not buried.
