Newton 3 — a behaviour-driven allocation engine

Newton 3

A behaviour-driven parking-space allocation engine.
The behaviour score is a pure fold over an append-only event log.

score(events, config, now)
The problem

What Newton 3 has to get right

  • Every allocation explainable to the user — GDPR Article 22 expects it.
  • Scoring that earns trust: rewards as well as penalties, context-aware — not penalties alone.
  • Per-tenant policy — weights configurable, not hardcoded.
  • One consistent model of the score — persistence and decay that don’t contradict each other.
  • All answering the loudest user voices: “allocation feels random” and “nobody tells me why.”
The idea

Don’t build subsystems. Reframe.

The behaviour score is not stored, mutated state. It is a pure function of an append-only event log, evaluated at a point in time.

score(events, config, now) =
  max(floor, base + min(rewards, cap) + penalties)

Everything else is a thin shell around that one function.

What the reframing delivers

Four hard requirements become properties of the fold

RequirementHow the fold delivers it
Always-current scoreDerived from the log on read — nothing to reset, never stale.
Fair, per-event decayEach event decays against its own timestamp.
Explainability (GDPR Art. 22)Per-event contributions are the explanation; they reconcile to the score.
Per-tenant policyConfig is a parameter; per-tenant = a different Config.
Fewer moving partsThe weekly decay Lambda is gone — decay is read-time.
Transparent by construction

Events in → score and a reconciling trace out

# GET /users/bob/behavior-score (real output) { "user_id": "bob", "score": 102, "tier": "Silver", "reward_cap_adjustment": 0.0, "config_version": "default", "evaluated_at": "2026-06-09T18:11:07Z", "recent_impacts": [ {"event": "unused_booking", "points": -2.57}, {"event": "carpool", "points": 4.46} ] }

This is the GDPR Article 22 surface. The score is the list of events that moved it — each with its decayed value — and the arithmetic reconciles.

Every allocation outcome carries its reason too. That answers “feels random” and “nobody tells me why.”

Mandatory complaint-analysis proposals

Two proposals, delivered

#1
Offence override

Config.offence_override force-ranks repeat offenders last. Threshold and window are tenant-configurable. Enforced only behind a proven detector.

#8

Where the layer acts

Behaviour is layer 3 — exactly where legacy was random

  • The sort is (restricted, group_priority, user_priority, −score). Behaviour only reorders users inside an equal-priority bracket.
  • 1,030 of 1,200 users sit in such a bracket — where the legacy system fell back to a random tie-break.
  • Randomness → a deterministic, explainable order. A shadow comparator proves whom it reorders before any cut-over.

Innovation · the AI stretch

ML where it earns its place — never where it breaks trust

Compose, don't couple. ML feeds capacity, not ranking. The score stays a pure, explainable fold; a black box never decides who gets a space.

  • Predictive no-show → overbooking — reclaim the seats no-shows waste. Shipped in analysis/predict.py (calibrated, 64% better than a mean baseline).
  • Anomaly detection on the event stream — catch ANPR misreads before they become penalties (the false-positive offence-detection risk).
  • LLM explanations built from the impact trace — grounded in the real numbers, so they can't hallucinate the score.

Where it would break trust:

  • Don't learn the ranking — a black-box sort brings back the exact "feels random / nobody tells me why" the project kills (and GDPR Art. 22).
  • The Z-tier trap — training on complaints teaches "complains-without-using" as a target. Filter it out.
  • Needs a real event log first — the store now captures it; today's baseline trains on reconstructed aggregates.

Worked example — an office has 80 spaces and ~8% of bookings no-show. Admit exactly 80 and ~6 sit empty every day. The model predicts ~92% attendance, so it admits 87 (80 ÷ 0.92): ~80 actually park, ~7 more people served each cycle — and the behaviour ranking still decides who, with the same explanation. The model only chose the number 87, never the people.
